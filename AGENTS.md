# Единый UiKit личных приложений

Канонический репозиторий — **SuselMan/UiKit**. Подключение в приложениях —
Git submodule, обычно `frontend/UiKit`. Не копировать компоненты в другой
репозиторий и не создавать параллельный UI-kit. Потребители перечислены в CONSUMERS.md.

## Границы библиотеки

Сюда относятся универсальные визуальные компоненты, иконки, токены, темы,
доступность и общее поведение интерфейса. Прежде чем писать локальный компонент,
проверь существующие компоненты и возможность их расширения.
Общий компонент без бизнес-логики следует вынести сюда, когда его универсальность
понятна из назначения либо подтверждена несколькими реальными применениями.
Не создавать заранее абстракции под гипотетические потребности.

В UiKit запрещены API-запросы приложений, сведения о пациентах/тренировках,
медицинские нормы, расчёт питания, бизнес-правила, хранилища/роуты конкретного
продукта и обращения к приватным адресам. Данные и обработчики приходят через props.
Графики и таблицы переносить только при отделении действительно общего механизма
от расчётов и смысла показателей; не объявлять медицинский экран универсальным.

## Общая стилистика

Применять общие токены цветов, шрифтов, отступов, радиусов, состояний и фокуса.
Новый общий вариант оформлять в UiKit через API компонента/токены.
Не перекрашивать и не переделывать внутренние классы компонента в каждом
приложении. Отличия продуктов задавать согласованной темой, содержимым и композицией.
Сохранять доступность, клавиатуру, мобильное управление и светлую/тёмную темы.

## Изменения UiKit и обновление потребителей

1. Развивать общие компоненты в UiKit, проверять затронутые компоненты и сборку.
2. Сохранять совместимость API, а несовместимые изменения и миграцию описывать явно.
3. С согласия владельца включать проверенные изменения в основную ветку UiKit.
4. Потребители обновляют gitlink на опубликованный SHA по мере необходимости;
   одновременное обновление и проверка всех потребителей не требуются.
5. Если задача включает обновление конкретного потребителя, проверить именно его
   затронутые сценарии и сборку; указать версию и результаты проверки.

Обновление сабмодуля в исходниках не означает автоматический production deploy.
Действующие сервисы и незавершённый новый стенд не переключать друг на друга.
Разрешения Git push/deploy и правила ресурсов берутся из общих правил владельца.
Не включать чужие изменения без просмотра и не переписывать историю.
Новые приложения сразу добавлять в CONSUMERS.md; удалённые потребители убирать
после проверки, что они больше не собираются с UiKit.

Новые цвета добавлять только при серьёзной необходимости и после согласования
с владельцем. Сначала использовать существующие токены и их прозрачность.
